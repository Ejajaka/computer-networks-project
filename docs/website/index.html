Real-Time DDoS Detection & Mitigation with eBPF and XDP

This website explains our entire project, from the very first concept to the final measured result. We reproduced a published research paper — an eBPF/XDP defense that stops DDoS floods inside the Linux kernel — and then added our own features: protection against SYN floods and a single combined program that fights UDP and SYN floods at the same time. Everything here is explained in simple words, with analogies, diagrams, and real numbers.

📄 Paper: Tolay 2025 · arXiv:2508.00851 UDP drop: 99.7% SYN drop (ours): 99.9% Combined: 99.8% Legit traffic: 0% dropped

Quick tour: the problem → key ideas → the paper → what we added → the code → the results.

1 The Problem

The Internet of Things (IoT) is a gold mine for attackers. Billions of small, cheap, often insecure devices are being turned into an army of zombie machines that attack the rest of the internet.

1.1 What is IoT?

IoT (Internet of Things) = everyday devices that connect to the internet: smart cameras, routers, doorbells, sensors, printers, fitness trackers. There are projected to be more than 75 billion of them. Most are built to be cheap, not secure — they have little memory, a weak CPU, and often ship with default passwords.

1.2 What is a DDoS attack?

DDoS = Distributed Denial of Service. It means: "many computers send so much junk at one target that the target can't do its real job anymore." It's like a thousand people crowding a single shop entrance — no real customer can get in.

The classic example — the Mirai botnet (2016)

An attacker hacked hundreds of thousands of IoT cameras and routers, turned them into an army of bots, and used them to flood websites with massive traffic. Huge parts of the internet went down. This proved that weak IoT devices are a serious global weapon.

Attacks keep growing: peak attacks now reach several terabits per second (a terabit = 1000 gigabits). Defending against this is hard, especially on the same weak devices being attacked.

1.3 Two attacks this project fights

🌊

UDP flood

The attacker blasts a huge number of UDP packets at the victim. UDP is the "fire and forget" internet protocol — no handshake needed — so it is trivially easy to flood with. The victim chokes on useless packets.

🤝

SYN flood

The attacker sends a flood of TCP "new connection" packets (SYN) but never finishes the handshake. The victim keeps reserving memory for half-open connections until it runs out and can no longer accept any real connection.

Both are volumetric attacks — their weapon is sheer quantity, not clever content.

1.4 Why normal firewalls fail

A normal firewall (like iptables on Linux) is a "gatekeeper in the middle of the building". It can stop bad guys — but only after the mail room has already opened every letter.

Here is the journey of a packet on a normal Linux computer:

📡 Network card (NIC) receives the packet
▼
💾 Kernel allocates memory for it — sk_buff
▼
🛂 Firewall (iptables / netfilter) finally sees it
▼
🖥️ Application receives it

The killer detail

By the time iptables sees a packet, the kernel has already spent memory and CPU on it. Under a flood, the victim burns all its resources before the firewall ever gets a chance to drop anything. The machine becomes unresponsive — the attack "wins."

So we need a guard at the very front door — on the network card itself, before any memory is wasted. That is exactly what XDP + eBPF let us do (next section). 💡

2 Background Concepts

To understand the project you only need three ideas: eBPF (safe code inside the kernel), XDP (the earliest possible spot to run it), and maps (shared memory the kernel program can use). Let's build them up one at a time.

2.1 The kernel and two "worlds"

Every operating system has a kernel — the core program that controls hardware. Everything else runs "outside" the kernel in user space.

  • Kernel space: fastest, can touch hardware, but a crash here = whole computer crashes.
  • User space: safe and flexible (your apps), but communication with hardware costs time.

Normally, custom network logic lives in user space — safe but slow. Getting kernel speed has traditionally meant writing a kernel module… which is dangerous (one bug = crash) and hard to distribute. eBPF changes this completely.

2.2 eBPF — "safe programmable kernel code"

eBPF (extended Berkeley Packet Filter) is a Linux technology that lets anyone write a small program and safely run it inside the kernel, without ever crashing the machine.

Why is it safe? — The Verifier

Before eBPF code is allowed to run, the kernel runs a strict checker called the verifier. It proves the program: (1) runs in bounded time — no infinite loops, (2) never reads past the end of a packet — no out-of-bounds access, (3) exits in a finite number of steps, and (4) only calls allowed helper functions. If any check fails, the program is rejected. This same safety check is why our whole project only needs to compile once with clang — if the verifier accepts it, it can't hurt the system.

Analogy: eBPF is like a vending machine that only accepts money and gives exact snacks — it physically cannot be tricked into doing anything else, because every possible action was pre-approved.

eBPF programs run at hook points — places inside the kernel where the program is "plugged in". We use the hook called XDP.

2.3 XDP — the front door of the network card

XDP (eXpress Data Path) is an eBPF hook that runs in the network driver, the instant a packet arrives on the network card — before the kernel allocates any memory (sk_buff) for it. It is the earliest possible point to make a decision.

An XDP program returns one of a few "verdicts":

VerdictMeaningUsed for
XDP_PASSLet the packet continue to the normal kernel stackGood / normal traffic
XDP_DROPThrow the packet away immediatelyAttack packets — the fastest possible block
XDP_TX / XDP_REDIRECTSend the packet back out / forward itAdvanced tricks (not needed here)

So with XDP: bad packet → dropped in microseconds at the front door, zero memory wasted. That is the "superpower" of this whole project. 🦸

2.4 eBPF maps — shared memory

An eBPF program often needs to remember things between packets. It uses maps — special key–value storage that both the kernel program and user-space programs can read and write.

Map typeWhat it isWhy we use it
BPF_MAP_TYPE_LRU_HASH A hash table that automatically forgets the least-recently-used entries when full Remember each sender's packet/SYN count, keyed by source IP — no manual cleanup needed
BPF_MAP_TYPE_PERCPU_ARRAY A tiny fixed-size array, one copy per CPU core Counters (total/dropped/alerts) written by many cores at once — no lock contention, blazing fast

Our kernel program uses a rate_map/syn_map (LRU hash, key = source IP) to track senders, and a stats_map (per-CPU array) to count how many packets were seen, dropped, and alerted. The tool bpftool map dump lets us read those numbers afterwards to get our results.

2.5 The two halves of the system

The whole design is hybrid — it deliberately splits the work:

⚡

In the kernel (eBPF/XDP) — the fast half

Look at every packet at the front door, track senders, and instantly drop anything above the rate limit. Uses almost no memory because nothing heavy is ever allocated.

🧩

Outside the kernel (controller.py) — the flexible half

A normal Python program reads the kernel's alert messages, permanently blocks the attacker's IP with a firewall rule, and logs everything. This part is easy to extend (send an email, a Telegram message, etc.).

Why split it?

Dropping packets needs raw speed → do it in the kernel. Deciding policy, notifying people, keeping records → do it in user space where it's easy to change. Best of both worlds. 🌍

3 The Paper We Reproduced

"eBPF-Based Real-Time DDoS Mitigation for IoT Edge Devices" — Abdurrahman Tolay, Istinye University, İstanbul, Türkiye. July 2025. Preprint on arXiv: 2508.00851.

3.1 The paper's idea, in one sentence

Put a smart guard on the network card itself (via eBPF + XDP) that notices when any one sender is flooding too fast, and discards that sender's packets before they consume any resources.

3.2 Threat model (what the paper assumes)

  • An attacker has compromised one or more IoT devices on a network (they become "bots").
  • The bots launch a volumetric DDoS — typically a UDP flood, and also mentions TCP SYN floods — at a target.
  • The attack appears as an abnormally high packet rate from each bot's IP address.

"Volumetric" = "bigness attack". The attacker wins by overwhelming quantity, so a how-fast-is-this-sender-going counter is the perfect detector.

3.3 System architecture (paper)

🤖 Bot / Attackersends flood(compromised IoT device)
▼
🖥️ Victim — IoT edge devicenetwork card → XDP hook
▼
🧬 eBPF program (in kernel)Rate detection + XDP_DROP
▼
🧩 User-space controller (Python)reads alerts → iptables block → notify

The crucial placement: the eBPF program sits at the XDP hook — before the kernel builds an sk_buff for each packet (see §2.3).

3.4 Detection logic (paper)

The eBPF program implements a per-source-IP, rate-based detector:

  1. Parse the Ethernet and IP headers to find the source IP of each packet.
  2. Count in an eBPF hash map: key = source IP, value = packet count.
  3. Compare the count to a threshold within a time window (e.g. 800 packets/second).
  4. Alert: if the threshold is breached, print an alert (with the attacker IP) to the kernel trace pipe via bpf_trace_printk().

3.5 Mitigation logic (paper)

  1. Immediate drop: Once an IP is flagged, its packets are dropped immediately by returning XDP_DROP — the fastest possible defense.
  2. User-space block: A Python controller watches the trace pipe; on an alert it inserts an iptables/nftables rule to block the IP persistently, and can even notify an admin via Telegram.

3.6 How the paper tested it

🐳

Docker simulation

A fake IoT network in Docker: a victim container, an attacker container running hping3, and a benign client. Attack speed ≈ 100,000 packets/s (~100 Mbps). Measured drop rate, CPU, and ping latency with the filter on vs. off.

🍓

Physical Raspberry Pi 4

A real Pi 4 (4 GB RAM, Linux 5.15) as the victim, a laptop attacking over LAN with iperf3 at up to 100 Mbps (~30,000 pps). NIC offloads (GRO/LRO) disabled for accurate counting.

The elegant "processing shield" insight

On the Pi, one CPU core went up to ~85% during a mitigated attack — but that was almost entirely the kernel process (ksoftirqd) handling interrupts and running the XDP program. That one core absorbed the whole flood, protecting the other cores and the applications. The device "fails operational" instead of failing completely.

3.8 Paper's limitations (that we're careful about)

  • Blind to content: it only measures rate, so it can't see malicious content inside encrypted packets, and can't catch "low-and-slow" attacks that fly under the rate limit.
  • Fixed thresholds: the limits are hard-coded numbers (see §10).
  • Kernel requirements: needs a modern Linux kernel with eBPF/XDP support.

4 Our Project — What We Did

We treated the paper as a blueprint: we reproduced its UDP-flood defense end-to-end, then improved it by adding SYN-flood protection and merging both into one program. Here is the exact story.

4.1 What we reproduced (the paper's part)

🌊

Docker-based UDP flood protection

A UDP flood (≈100 Mbps) against a victim container. An eBPF/XDP program in the victim detects a sender exceeding 800 packets/second and drops its packets at the network card. We measured a 99.7% drop rate — matching (and slightly beating) the paper's ~99%.

🔗

Hybrid kernel + user-space controller

Same design as the paper: kernel program drops at the NIC, a Python controller (controller.py) reads the alerts, adds an iptables block for the attacker IP, and logs events to alerts.log.

4.2 What we added (our new features) — the important part

FeatureIn the paper?In our project
UDP flood protection ✅ Yes Reproduced — 99.7%
SYN flood protection ❌ Not covered ✨ Added by us — 99.9%
Both attacks in ONE eBPF program ❌ No (only UDP) ✨ Added by us — combined 99.8%
Kernel + controller hybrid design ✅ Yes ✅ Same design

4.3 The SYN flood feature — how it works

A UDP flood is about packets per second. A SYN flood is about connection attempts per second. So our SYN detector:

  1. Only looks at TCP packets where the SYN flag is set and the ACK flag is clear — i.e. "please start a new connection." (A normal TCP handshake's 2 SYNs are the tiny exception that always passes.)
  2. Counts those per source IP in its own map (syn_map).
  3. Drops a sender's SYNs when it exceeds 200 connection attempts/second.

4.4 The combined program (our main program)

Instead of two separate filters, we wrote one XDP program — ddos_filter_kern.c — that handles both classes of traffic in a single pass over each packet:

  • If the packet is UDP → run the UDP rate check (≥ 800 pps → drop).
  • If the packet is TCP with SYN=1, ACK=0 → run the SYN rate check (≥ 200 new-conn/s → drop).
  • Everything else (ICMP, normal TCP traffic, …) → XDP_PASS.

5.1 Hello XDP — proving the front door exists (hello_xdp.c)

Before doing anything clever, we check that XDP works at all on this machine. This tiny program parses the Ethernet + IP headers of every packet and prints a friendly message about what it saw. 

#include <linux/bpf.h>
#include <linux/if_ether.h>
#include <linux/ip.h>
#include <bpf/bpf_helpers.h>

SEC("xdp")                       // attach this at the XDP hook
int xdp_hello(struct xdp_md *ctx) {
    void *data_end = (void *)(long)ctx->data_end;   // end of the packet
    void *data     = (void *)(long)ctx->data;       // start of the packet

    struct ethhdr *eth = data;
    if ((void *)(eth + 1) > data_end) return XDP_PASS;  // safety: bounds check

    struct iphdr *ip = (void *)(eth + 1);
    if ((void *)(ip + 1) > data_end) return XDP_PASS;   // safety: bounds check

    bpf_printk("hello_xdp: proto=%d src=%pI4 dst=%pI4\n",
               ip->protocol, &ip->saddr, &ip->daddr);   // print to trace pipe

    return XDP_PASS;  // let every packet through -- we're only testing
}

char _license[] SEC("license") = "GPL";  // required for helper calls

Two things to notice, because they appear in every program: the bounds checks (the verifier demands them — we must prove we never read past the packet) and SEC("xdp") (marks the function as an XDP program).

5.2 The UDP filter — reproducing the paper (udp_filter_kern.c)

This is the paper's detector, written in ~90 lines. Explained step by step:

#define RATE_THRESHOLD 800              // more than 800 packets/second = flooding
#define WINDOW_NS      1000000000ULL     // the time window: 1 second, in nanoseconds

struct pkt_count {                      // what we remember about each sender
    __u64 count;                        // how many packets they sent
    __u64 last_ts;                      // when we (re)started counting
};

/* map #1: per-sender packet counter. key = source IP, value = pkt_count.
 * LRU_HASH = auto-forgets old senders when full. */
struct { __uint(type, BPF_MAP_TYPE_LRU_HASH); __uint(max_entries, 65536);
         __type(key, __u32); __type(value, struct pkt_count); } rate_map SEC(".maps");

/* map #2: global statistics (total seen / dropped / alerted).
 * PERCPU_ARRAY = one copy per CPU core so many cores can count without locks. */
struct stats { __u64 total; __u64 dropped; __u64 alerted; };
struct { __uint(type, BPF_MAP_TYPE_PERCPU_ARRAY); __uint(max_entries, 1);
         __type(key, __u32); __type(value, struct stats); } stats_map SEC(".maps");

SEC("xdp")
int xdp_udp_filter(struct xdp_md *ctx) {
    void *data_end = (void *)(long)ctx->data_end;
    void *data     = (void *)(long)ctx->data;

    struct ethhdr *eth = data;
    if ((void *)(eth + 1) > data_end) return XDP_PASS;        // bounds check
    if (eth->h_proto != bpf_htons(ETH_P_IP)) return XDP_PASS; // only IPv4

    struct iphdr *ip = (void *)(eth + 1);
    if ((void *)(ip + 1) > data_end) return XDP_PASS;         // bounds check
    __u32 src_ip = ip->saddr;                                 // WHO sent this?

    __u32 key = 0;
    struct stats *st = bpf_map_lookup_elem(&stats_map, &key);
    if (st) __sync_fetch_and_add(&st->total, 1);              // +1 "seen"

    __u64 now = bpf_ktime_get_ns();                           // current time (ns)

    struct pkt_count *pc = bpf_map_lookup_elem(&rate_map, &src_ip);
    if (!pc) {                                                // first time this sender
        struct pkt_count init = { .count = 1, .last_ts = now };
        bpf_map_update_elem(&rate_map, &src_ip, &init, BPF_ANY);
        return XDP_PASS;                                      // not yet flooding
    }

    if (now - pc->last_ts >= WINDOW_NS) {                     // window expired?
        pc->last_ts = now; pc->count = 1;                     // reset for new second
        return XDP_PASS;
    }

    pc->count++;                                              // same-second, keep counting
    if (pc->count > RATE_THRESHOLD) {                         // BUSTED
        if (st) { __sync_fetch_and_add(&st->dropped, 1);
                 __sync_fetch_and_add(&st->alerted, 1); }
        if (st && st->alerted % 1000 == 1)                   // throttle: print ~every 1000
            bpf_printk("UDP FLOOD DETECTED from %pI4 count=%llu\n", &src_ip, pc->count);
        return XDP_DROP;                                      // throw it away, NOW
    }
    return XDP_PASS;                                          // still polite, let it through
}

Why atomics (__sync_fetch_and_add)?

Many CPU cores run this program at once (one per packet). Adding to a shared counter from many cores at the same time must be atomic, or numbers get corrupted. For per-CPU maps we don't even need locks — each core has its own copy.

5.3 The SYN filter — our first new feature (syn_filter_kern.c)

Same structure, but now we filter on connection attempts, not all packets:

#define SYN_THRESHOLD 200               // > 200 new connections/second = flooding
#define SYN_WINDOW_NS 1000000000ULL      // 1-second window

struct syn_count { __u64 count; __u64 last_ts; };   // per-sender connection counter

struct { __uint(type, BPF_MAP_TYPE_LRU_HASH); __uint(max_entries, 65536);
         __type(key, __u32); __type(value, struct syn_count); } syn_map SEC(".maps");

struct syn_stats { __u64 syn_total; __u64 syn_dropped; __u64 syn_alerted; };
struct { __uint(type, BPF_MAP_TYPE_PERCPU_ARRAY); __uint(max_entries, 1);
         __type(key, __u32); __type(value, struct syn_stats); } syn_stats_map SEC(".maps");

SEC("xdp")
int xdp_syn_filter(struct xdp_md *ctx) {
    ...
    if (ip->protocol != IPPROTO_TCP) return XDP_PASS;    // only TCP

    struct tcphdr *tcp = (void *)(ip + 1);
    if ((void *)(tcp + 1) > data_end) return XDP_PASS;   // bounds check

    /* KEY: only "please open a new connection" packets = SYN set + ACK clear.
       Handshake replies (SYN+ACK) and data packets pass untouched. */
    if (!(tcp->syn) || tcp->ack) return XDP_PASS;

    __u32 src_ip = ip->saddr;
    ...same 1-second sliding counter as UDP...
    if (sc->count > SYN_THRESHOLD) {
        ... __sync_fetch_and_add(&st->syn_dropped, 1); ...
        bpf_printk("SYN FLOOD DETECTED from %pI4 count=%llu\n", &src_ip, sc->count);
        return XDP_DROP;
    }
    return XDP_PASS;
}

The neat trick: a normal TCP connection only sends 2 SYNs total — that's a few orders of magnitude below 200/second, so real users are never touched.

5.4 The combined program — our main program (ddos_filter_kern.c)

We merge both detectors into one XDP function. Now a single attached program protects against UDP floods AND SYN floods simultaneously. It has both maps (rate_map + syn_map) and one combined stats_map with six counters (udp_total, udp_dropped, udp_alerted, syn_total, syn_dropped, syn_alerted). 

SEC("xdp")
int xdp_ddos_filter(struct xdp_md *ctx) {
    ... parse Ethernet + IP headers, bounds checks ...
    __u32 src_ip = ip->saddr;
    __u32 key = 0;
    struct stats *st = bpf_map_lookup_elem(&stats_map, &key);

    if (ip->protocol == IPPROTO_UDP) {
        /* ---- UDP flood detection (packets/second) ---- */
        struct udphdr *udp = (void *)(ip + 1);
        if ((void *)(udp + 1) > data_end) return XDP_PASS;
        if (st) __sync_fetch_and_add(&st->udp_total, 1);
        ...
        if (pc->count > RATE_THRESHOLD) {           // 800 pps
            ... bpf_printk("UDP FLOOD DETECTED from ...");
            return XDP_DROP;
        }
        return XDP_PASS;
    }

    if (ip->protocol == IPPROTO_TCP) {
        /* ---- SYN flood detection (connection attempts/second) ---- */
        struct tcphdr *tcp = (void *)(ip + 1);
        if ((void *)(tcp + 1) > data_end) return XDP_PASS;
        if (!(tcp->syn) || tcp->ack) return XDP_PASS;   // only new-connection SYNs
        if (st) __sync_fetch_and_add(&st->syn_total, 1);
        ...
        if (sc->count > SYN_THRESHOLD) {            // 200 conns/sec
            ... bpf_printk("SYN FLOOD DETECTED from ...");
            return XDP_DROP;
        }
        return XDP_PASS;
    }

    return XDP_PASS;   // ICMP and everything else passes
}

Why combine them?

One program = one attach point = one place to manage, and both defenses share the same packet parse (Ethernet + IP headers are parsed once, not twice). Attacking with UDP and SYN at the same time still gets a combined 99.8% drop rate.

5.5 The user-space controller (controller/controller.py)

The "flexible half". It reads the kernel's trace_pipe, finds alert lines like UDP FLOOD DETECTED from 172.30.0.20, and reacts. 

import re, subprocess, sys, time
from datetime import datetime

TRACE_PIPE = "/sys/kernel/tracing/trace_pipe"
VICTIM     = "victim"
LOG_FILE   = "results/alerts.log"

SELF_IPS = {"172.30.0.10", "172.30.0.1", "127.0.0.1"}   # never block these

ALERT_RE = re.compile(r"(UDP FLOOD|SYN FLOOD) DETECTED from (\d+\.\d+\.\d+\.\d+)")
BLOCKED  = set()                                         # remember already-blocked IPs

def block_ip(ip):
    """Add a persistent iptables rule INSIDE the victim container."""
    return run(["docker", "exec", VICTIM, "iptables",
                "-A", "INPUT", "-s", ip, "-j", "DROP"])[0] == 0

def main():
    with open(TRACE_PIPE, "r") as tp:      # blocking read; new lines appear live
        for line in tp:
            m = ALERT_RE.search(line)
            if not m:            continue
            kind, ip = m.group(1), m.group(2)
            if ip in SELF_IPS or ip in BLOCKED: continue
            BLOCKED.add(ip)
            log(f"{kind} detected from {ip} -- blocking via iptables")
            if block_ip(ip): log(f"BLOCKED {ip} (iptables rule added in {VICTIM})")
            else:            log(f"FAILED to block {ip}")

The % 1000 == 1 throttle in the kernel program means the pipe doesn't drown in messages — the controller gets meaningful alerts, not millions.

# victim   : gets the filter + server (privileged so XDP works inside it)
docker run -d --name victim  --network ddos-net --privileged \
  --cap-add NET_ADMIN --cap-add SYS_ADMIN --cap-add SYS_RESOURCE \
  --ip 172.30.0.10 ubuntu:22.04 sleep infinity

# attacker : only needs hping3 to flood
docker run -d --name attacker --network ddos-net --ip 172.30.0.20 ubuntu sleep infinity
# benign   : sends normal traffic
docker run -d --name benign   --network ddos-net --ip 172.30.0.30 ubuntu sleep infinity

docker exec -d victim iperf3 -s -p 5201          # UDP server on the victim

Then the filter is loaded into the victim with bpftool and pinned to its network interface: bpftool prog loadall ddos_filter_kern.o /sys/fs/bpf/ddos followed by ip link set dev eth0 xdp pinned /sys/fs/bpf/ddos/xdp. That's the moment the virtual network card starts filtering!

6 The Detection Algorithm — Step by Step

Let's zoom into the brain of the system — a sliding 1-second window rate counter per source IP — with a concrete example and a live interactive demo.

6.1 The algorithm, in plain words

For a given sender (say 172.30.0.20):

  1. First packet ever seen: store count = 1 and remember the current time.
  2. Next packets: if less than 1 second has passed since we started counting, add 1 to their count.
  3. New second begins: if 1 second has passed, reset the counter to 1 and restart the window.
  4. Threshold: if, inside one window, the count goes above the limit — 800 for UDP, 200 for SYN — every further packet from that sender in that window is XDP_DROP'd.

It's a "sliding" window because each sender's window restarts whenever a second passes for that specific sender — senders don't share one global clock.

6.2 A worked example (UDP, limit 800)

TimeWhat arrives from the senderCounterDecision
t = 0 mspacket #11PASS
t = 100 mspacket #22PASS
…… (packet rate climbs)…PASS
t = 799 mspacket #800800PASS (limit reached, not passed)
t = 810 mspacket #801801DROP — flooding!
t = 820 ms…packets #802, #803, …>800DROP
t = 1000 ms— window expires —reset → 1fresh chance (but floods keep coming)

Important subtlety

The 800th packet still passes — the check is count > 800, not count >= 800. So a legit sender running at almost exactly the limit stays safe. This matters for §10.

7.2 Why the victim container needs privileges

Attaching an XDP program and controlling the interface requires NET_ADMIN, SYS_ADMIN, and --privileged. Do not copy these flags to containers on a public network — it's only acceptable inside a private testbed.

7.3 The attack tools

  • hping3 -2 -p 5201 --flood 172.30.0.10 → UDP flood (the -2 = UDP mode). Four of these at once ≈ 100 Mbps.
  • hping3 -S -p 5201 --flood 172.30.0.10 → SYN flood (-S = TCP SYN mode).
  • iperf3 -c 172.30.0.10 -p 5201 -u -b 3M -t 5 → benign UDP traffic at 3 Mbps (~250 packets/s, safely under the 800 limit).

7.4 The demo script (demo.sh) — one command, whole story

The one-shot demo does every step and prints the important numbers:

  1. Make sure containers are running.
  2. Start the iperf3 UDP server on the victim.
  3. Install missing tools (bpftool, iptables) and attach the combined ddos_filter_kern.o to the victim's eth0 XDP hook.
  4. Start controller.py.
  5. Launch the UDP flood for 8 s → read drop_rate.
  6. Launch the SYN flood for 8 s → read drop_rate.
  7. Send benign traffic → check extra drops = 0.
  8. Show the controller log (detections + blocks).

The drop rates come from reading the kernel's stats_map with bpftool map dump name stats_map — real live kernel counters, not estimates.

Why our CPU numbers don't change much (but the paper's do)

Our computer has 16 cores, so a ~100 Mbps flood never fully saturates a single core, whether the filter is on or off. The paper's dramatic CPU win (45% → 12%) appears on small devices like a Raspberry Pi, where one core is the whole machine. The result that counts here — the ~99% drop rate — reproduces perfectly, and that's the core claim of the paper.

8.5 End-to-end: filter + controller together

When the controller ran alongside the filter, it:

  1. Read the kernel alert "SYN FLOOD detected from 172.30.0.20".
  2. Added an iptables rule inside the victim blocking 172.30.0.20.
  3. Saved the event to alerts.log.

Detection → blocking happened in < 2 seconds, matching the paper's end-to-end response time.

10 Limitations (Be Honest)

No defense is perfect. These are the known weaknesses — we keep them visible on purpose.

🎯

Fixed thresholds

800 pkts/s (UDP) and 200 conns/s (SYN) are hard-coded numbers. A normal user faster than the limit looks like a flooder and gets blocked too. The paper acknowledges this (its §6.3).

👁️

Blind to content

We only measure rate. We cannot detect "low-and-slow" attacks (small but crafted traffic), application-layer attacks, or malicious content hidden inside encrypted payloads.

📼

Per-sender, not distributed

A true DDoS spreads across thousands of IPs — each well under the limit. Our per-source-IP rate check would miss a huge, slow, distributed flood.

🐧

Linux + modern kernel needed

eBPF/XDP needs a reasonably modern Linux kernel; many old or non-Linux IoT chips can't run it.

🛡️

eBPF itself must be hardened

If attackers can load their own eBPF programs, they could disable our filter. Production needs strict load permissions (e.g. CAP_BPF only for admins).

📋

Management at scale

Deploying and updating filters across thousands/millions of devices needs secure orchestration — a research area in itself.

Bottom line: this is a specialist tool — a fast, first-line guard against volumetric floods — not a complete security suite. Defense in depth (cloud scrubbing, firewalls, anomaly detection) remains necessary.

11 Future Work

Where this project naturally goes next — inspired by the paper's own outlook and by what we learned.

🤖

Adaptive thresholds with ML

Replace the fixed 800/200 with a model that learns each network's normal baseline and updates the limits dynamically inside the eBPF map.

📡

More attack classes

Detect IoT-protocol floods (MQTT, CoAP) and "low-and-slow" application-layer attacks — needs deeper stateful analysis in the program.

🌐

Distributed detection

Combine per-device counters into an orchestration layer that recognizes distributed multi-IP floods.

🛩️

Secure fleet management

OTA updates, central monitoring dashboards, and policy enforcement across thousands of IoT devices.

12.3 The manual way — to see each part

A Build the filters

make -C engine

B Create the fake network (victim/attacker/benign)

sudo bash testbed/setup_testbed.sh

C Attach the combined filter to the victim's network card

sudo docker cp engine/ddos_filter_kern.o victim:/tmp/ddos_filter_kern.o
sudo docker exec victim bash -c '
  BPF=$(ls /usr/lib/linux-tools/*/bpftool 2>/dev/null | head -1)
  rm -rf /sys/fs/bpf/ddos
  $BPF prog loadall /tmp/ddos_filter_kern.o /sys/fs/bpf/ddos
  ip link set dev eth0 xdp pinned /sys/fs/bpf/ddos/xdp'
# expected: "xdp" appears when you run:  ip link show dev eth0

D Start the controller (observer that blocks IPs)

sudo bash testbed/start_controller.sh

E Launch a UDP flood, then read the counters

for i in 1 2 3 4; do sudo docker exec -d attacker hping3 -2 -p 5201 --flood 172.30.0.10; done
sleep 8
sudo docker exec attacker pkill -9 hping3
sudo docker exec victim bash -c '
  BPF=$(ls /usr/lib/linux-tools/*/bpftool 2>/dev/null | head -1)
  $BPF map dump name stats_map'   # expect udp_dropped ≈ 99% of udp_total

F Launch a SYN flood and check again (hping3 -S … --flood) → syn_dropped ≈ 99% of syn_total.

G Prove normal traffic is untouched

sudo docker exec benign iperf3 -c 172.30.0.10 -p 5201 -u -b 3M -t 5
# re-read stats_map → udp_dropped must NOT have increased
sudo bash testbed/report.sh   # optional: full WITHOUT vs WITH filter report

H Clean up when done

sudo docker exec victim ip link set dev eth0 xdp off
sudo pkill -f controller.py
sudo docker rm -f victim attacker benign
sudo docker network rm ddos-net
